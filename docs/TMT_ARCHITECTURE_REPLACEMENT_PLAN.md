**Confirmed defects and differences.** Token, version and windowed data replies can accept `success: "false"` as successful, including an apparently empty data reply. The image contract includes package `tppid`, `fsn`, `pack_level`, `pack_size`, `subpack_unit` and `pack_unit`, plus nested variants and views. Ignoring the documented fields or rejecting their numeric values loses source fidelity. ImageList needs durable metadata without bulk image payload storage. The offset-free expiry currently depends on the runtime timezone with a fallback lifetime. Admin and environment configuration enforce different HTTPS rules. A canonical policy must validate HTTPS/TLS and redirects, without assuming the provider timezone. CLI and Queue differ in retries, token refresh and optional endpoint failure handling. Legacy CLI coverage lookup can include checkpoints from failed or stale runs, whereas candidate coverage derives from an accepted base and pinned plan. Keep windows, overlap and completion criteria explicit. Treat the 365-day window, 30-day overlap and 2013-01-01 lower bound as application policies.

**Unresolved upstream semantics.** Confirm MasterTMT ordering across windows, status changes and cancellation scope, same-date duplicates and supersession for RegNo/ATC/NLEM, and effective identity/removal for Concept and Relationship. A material change to ambiguous latest values requires evidence. Preserve dated and multi-value history, and distinguish source rows, normalized keys and derived effective values. Absence from any response does not imply deletion. GPU 764169 remains a sentinel. Evaluate broader relationship consistency against upstream evidence before expanding blocking rules.

**Consumer findings.** Dashboard and Mapping share facility-scoped lifecycle counts, while Admin currently resolves some metrics and the active pointer separately. Standards MasterTMT totals can include cancelled rows. A fallback live count can diverge when the browser correctly fails closed on an unavailable pointer. Search and detail requests can observe different generations, and a row's source version can differ from the accepted dataset's version. Verify and label these distinctions in Dashboard, Standards, detail, GPU-to-TPU, Catalog, Mapping, Export and Admin. Preserve the existing Catalog reconciliation and Mapping generation checks, and the generation-bound export preview and stale-token rejection. See [dataset selection](../src/modules/standards/dataset-selection.ts), [candidate pointer](../src/modules/tmt/candidate-pointer.ts) and [export service](../src/modules/exports/service.ts).

## Approved replacement rules

- Deliver one canonical TMT module, API client, parser contract, persistence path, sync engine and dataset resolver. Build and verify the replacement before retiring the current implementation. Use an isolated development branch and approved disposable test databases. No permanent second TMT stack, new `tmt-v3`/`tmt-new`/`tmt-final` production module, silent legacy fallback or mixed dataset reads. Keep compatibility names until dependency checks support retirement. Preserve current routes, public APIs, responsive UI and user workflows.
- Every consumer must resolve one authoritative dataset and pin its identity and generation for each operation. Full Sync builds a complete validated baseline. Incremental stages and persists actual changes without cloning the entire accepted dataset per run. Require approval, atomic publication, generation checks, recovery, manifests, rollback, provenance and immutable audit evidence. Make validation policies for Full and Incremental explicit. Keep ambiguous source values and do not infer deletions from absence.
- Evaluate three storage designs before selection. **Atomic delta application** needs a measured transaction budget, generation-pinned readers and a durable inverse/rollback record. **Immutable Full base plus bounded overlays** merits early evaluation for small changes and pointer rollback. Set limits on overlay depth, query cost and compaction. **Row-level versioning** can provide effective reads per generation and retain fine-grained history, with greater index, lineage and rollback complexity. Stage 02 selects after isolated TiDB-compatible measurements, including worst-case transaction size, locks, retries, RU, indexes, effective read latency, rollback and retention. No paid infrastructure without owner approval.
- Bound Full snapshots and failed-candidate retention. Reserve recovery capacity, retain manifests and audit evidence, and define who may archive or delete data. Never delete Production data before the replacement is verified, owner-approved and recoverable. Production cutover and legacy data deletion require separate approvals. Do not edit applied migrations or reset their journal.
- TMT and TTMT remain independent. Drugtype `01` maps only to eligible active TMT TPU; `10` maps only to eligible TTMT products. Preserve source/code/level identity, mappings and lifecycle, acknowledgements, reconciliation, Full/Delta exports and history/checkpoints, stale-preview guards, users, facilities, JHCIS catalogs, TTMT, and audit/sync history. Keep Combined Dataset Release OFF. Never access port `3333` or `jhcisdb`. Do not inspect, modify, delete, expose or commit local secrets or credential files.

| 06 — Production Cutover | Separate owner approval for preparation and deployment scope. | 07 — Legacy Cleanup | Verify no reader, writer, job, route or fallback depends on the retired implementation. Archive old TMT data and evidence first. | Dependency, backup, restore and rollback gates plus separate owner approval before deleting data or removing obsolete tables/flags. Finish focused regression and reconcile docs. Preserve migration history and all historical documents. |
